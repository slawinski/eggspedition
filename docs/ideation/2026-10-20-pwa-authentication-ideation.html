Eggspedition · Authentication ideas

A sign-in that brings you back to the same app

Passkeys are the strongest direction for routine return visits. Real email codes are the closest alternative to today’s flow. Either can work alongside longer session continuity and a clear way to reconnect the existing installation.

Focus: Replace the frustrating email sign-in experience that currently sends the user to a browser and leads them to delete and reinstall the home-screen PWA after losing access.

Two separate problems: the current sign-in uses a clickable magic link, so completion depends on the context that opens it. Sessions also expire after a fixed 30 days without ordinary renewal.

A passkey or an entered code can make reauthentication easier. Session renewal can make automatic reauthentication less frequent. Neither means an intentional signout should leave the device authenticated.

Codebase Context

  • “OTP” currently means a magic link. The login screen accepts an email and shows “We’ve sent a squishy magic link.” It has no code-entry step. The email opens /api/auth/verify, which establishes the cookie in the context handling verification. See src/routes/login.tsx:29–82 and src/services/auth.api.ts:47–60.
  • Regular use does not extend the session. The JWT expires at 30d; the cookie lasts 30 days. The normal session reader verifies the token without reissuing it. Some household actions do reissue a session. See src/lib/auth-utils.ts:8–22, src/services/auth.api.ts:6–19, and src/services/household.api.ts:18–31,81–94.
  • The same icon launches the root URL. The manifest uses root scope, root start URL, and standalone display. Without a session, the root renders the marketing landing page, including installation guidance. That may reinforce the impression that a signed-out installation needs replacing; the effect has not been observed on the user’s device.
  • Reinstallation is not a coded requirement. Logout deletes the cookie and clears selected query/localStorage data. The service worker separately caches navigation responses and can serve cached pages offline. Neither cookie-context isolation nor stale cache has been established as the cause of the reported loop.
  • Existing households have a durable identity anchor. Memberships reference a user UUID. Login currently resolves that user through email. New sign-in methods can therefore be attached to the existing identity, rather than creating another household member.
  • Product fit: a shared grocery list with passwordless simplicity, offline-first use, and 30–90-day sticky-session intent. Shopping interruptions matter more than authentication feature breadth.

Evidence limits: no device/OS/browser reproduction was performed. Current MDN WebAuthn documentation was checked through Context7; broad web search and a vendor comparison were unavailable. That documentation establishes the mechanism, not compatibility on the user’s installed PWA. No application code was changed.

1. Passkeys for returning sign-in

Once someone has authenticated, offer to add a passkey to their existing account. When they later need to sign in through the home-screen app, they approve their device’s authenticator prompt—such as biometrics or device PIN—instead of opening email. Keep a recovery route for unavailable credentials and unsupported contexts.

Basis
external: MDN’s Web Authentication API describes server challenges, credentials tied to a user identity, stored public keys, and server validation. direct: src/routes/login.tsx:57–82 has only the magic-link flow; src/db/schema.ts:3–8 already provides a UUID account anchor.
Rationale
This changes the everyday authentication gesture and removes mail-link navigation from returning sign-in. It directly addresses the user’s desire for a friendlier replacement. Pairing it with #3 and #4 would address interruption frequency and recovery presentation separately.
Downsides
Enrollment, credential management, origin/RP configuration, server verification, and lost-credential recovery are new work. Support needs checking in the actual installed app. A passkey does not make a session permanent, and first enrollment still needs a trustworthy way into the existing account.

Closest alternativeA · In-app sign-in

2. Enter an email code in the installed app

Send a short-lived code that the user enters in the same installed app that requested it. Reading the email can happen in any mail client; finishing authentication happens back in Eggspedition. The waiting screen can retain the invitation or grocery action and offer resend and change-email recovery.

Basis
reasoned: today’s screen has no code input (src/routes/login.tsx:57–82), and the message tells the recipient to click a URL (src/services/auth.service.ts:125–147). Returning proof as a code avoids depending on that URL opening the right app context.
Rationale
This would be actual email OTP, unlike the current magic link. It changes fewer user concepts than passkey enrollment and offers a direct way to complete sign-in inside the existing PWA.
Downsides
Still depends on email delivery and an inbox round trip. Entry/paste can be annoying. Short codes need suitable attempt limits, expiration, and single-use enforcement; the current high-entropy link-token scheme cannot simply be shortened without reconsidering those protections.
Confidence
90%
Complexity

Supporting improvementB · Session continuity

3. Keep active personal devices signed in

Let successful authenticated use renew a remembered device’s session within bounded inactivity and maximum-lifetime policies. Weekly use would no longer count down toward a surprise deadline set a month earlier. An unused device eventually asks again; explicit signout still ends access.

Basis
direct: src/lib/auth-utils.ts:12 uses .setExpirationTime('30d'). src/services/auth.api.ts:6–19 reads and verifies the token without renewing it. The product’s sticky-session intent is 30–90 days to avoid aisle-lockout (SPEC.md:25).
Rationale
Reducing avoidable authentication events matters regardless of which sign-in method wins. This is the clearest code-grounded reason a regular shopper might encounter recurring automatic expiration.
Downsides
The cause of this user’s sign-offs is still unverified. Renewal cannot fix intentional logout or storage removal. Session duration, renewal, revocation, and stale authorization need a coherent policy; merely increasing both expiry numbers would not settle those choices.
Confidence
93%
Complexity

Supporting improvementC · Same-install recovery

4. Reconnect through the same home-screen icon

A signed-out installed app can say “Sign in to reconnect this app” and offer an authentication path that completes there. It can distinguish being offline from having an expired session or having deliberately signed out. The existing icon remains the place to return; installation advice belongs to first-time visitors.

Basis
direct: public/manifest.json:6–8 launches / in standalone mode. src/routes/index.tsx:54–59 renders LandingPage without a session, and src/components/landing/LandingPage.tsx:187–189 tells visitors to install from their browser.
Rationale
The current presentation treats an installed, signed-out user like a new website visitor. A reconnect experience directly challenges the reported reinstall ritual and belongs alongside a working in-app authentication method.
Downsides
Copy alone does not establish a session in the PWA. Authentication-aware navigation/cache behavior and stale-state handling need checking. No cache reset or removal of local shopping data is justified merely because the user reported reinstalling.

Alternative email flowA · In-app sign-in

5. Let email approve the waiting app

Keep the click-email gesture, but make it approve a sign-in request waiting in the original installed app. The browser confirms approval; the user returns to their existing icon, where the app completes its own bound request and establishes its session. The browser need not share its cookies with the PWA.

Basis
reasoned: the current callback sets the cookie (src/services/auth.api.ts:54–60) and redirects into the product (src/routes/api/auth/verify.tsx:30–34). Separating approval from app-side session delivery removes the need to rely on the callback’s browsing context.
Rationale
Useful if clicking email is otherwise comfortable and the handoff is the real problem. It can preserve the familiar gesture while making the originating installation the destination.
Downsides
More custom protocol work than entering a code: request binding, expiring approval, one-time redemption, cancellation, and app-resume behavior. A public request ID or “return to app” message alone would not establish trustworthy authentication. Email switching remains.

Migration foundationD · Account continuity

6. One account, replaceable sign-in methods

Attach a passkey or another verified sign-in route to the user’s existing account. Changing a credential should preserve the same household membership and person, rather than silently creating a new account. Email replacement and recovery would prove ownership of that existing account, not just possession of a newly supplied inbox.

Basis
direct: users have UUID primary keys and unique emails (src/db/schema.ts:3–8); memberships reference user IDs (:16–23). Magic-link verification finds or creates a user through email (src/services/auth.service.ts:166–174).
Rationale
The database already has a durable identity independent of the sign-in gesture. Preserving it makes a replacement useful to current households and supports future recovery without duplicate members.
Downsides
A supporting foundation, not a friendlier gesture by itself. Credential linking, identity normalization, admission rules, and recovery authorization add work. Household invitations grant access; they are not evidence of ownership of another member’s account.

Later recovery optionD · Account continuity

7. Approve this installation from a signed-in device

A signed-out installed app presents a short-lived pairing request. An already-authenticated browser or another personal device explicitly approves that installation into the same account. If the browser is signed in but the home-screen app is not, the working session becomes a recovery route instead of a dead end.

Basis
reasoned: authenticated access is anchored in session.userId (src/lib/middleware.ts:16–49), and memberships attach to that user UUID. A surviving authenticated session can authorize a deliberately matched installation without assuming cookie sharing. There is no existing device/session pairing store.
Rationale
Matches “I am signed in, but in the wrong place” and helps when a second device still works. It preserves personal identity rather than repurposing a household invite.
Downsides
Needs a surviving session and a carefully bound, expiring approval. Adds target-confirmation and phishing concerns plus a device-management model. For this app, it is likely more work than passkeys or entered email codes and is not the first direction to pursue.
