# Database Migrations — Spec

Status: **Proposed** (not yet implemented). Owner: engineering.

## 1. Problem

The project currently applies schema changes by running `drizzle-kit push` at
**boot time** (`package.json` → `start` → `db:migrate`).

Problems this causes:

1. **Boot-time prompt / 502.** `drizzle-kit push` prompts interactively when it
   detects destructive changes (e.g. `DROP TABLE`). In the non-interactive
   production container the prompt hangs or aborts, the `&&` chain never reaches
   the server, and the reverse proxy returns `502 Bad Gateway`. This is exactly
   what happened after the Quick Add removal dropped `quick_add_items`.
2. **No review.** Schema changes ship as a side effect of `push`, not as a
   reviewed artifact. Nobody sees the DDL before it hits production.
3. **No history / rollback.** There is no versioned record of what changed or
   when; "rollback" means hand-writing reverts.
4. **`--force` is a blunt instrument.** The current stopgap (`drizzle-kit push
   --force`) auto-applies destructive changes with no audit trail and no way to
   catch a mistake before it executes.

## 2. Goal

Replace boot-time schema push with **versioned, reviewed SQL migrations**
generated by `drizzle-kit generate` and applied by `drizzle-kit migrate`.

Non-goals: this spec does **not** change the ORM, the `src/db/schema.ts`
source-of-truth model, or the Postgres dialect.

## 3. Current vs target

| | Current | Target |
| --- | --- | --- |
| Source of truth | `src/db/schema.ts` | `src/db/schema.ts` (unchanged) |
| DDL artifact | none (implicit) | `drizzle/*.sql` (versioned, committed) |
| Apply mechanism | `drizzle-kit push` on boot | `drizzle-kit migrate` (idempotent, non-interactive) |
| History | none | `drizzle/meta/_journal.json` + `__drizzle_migrations` table |
| Review | none | PR review of generated `.sql` |
| CI safety | none | `drizzle-kit check` (drift gate) |

## 4. Proposed workflow

### Develop

1. Edit `src/db/schema.ts`.
2. Run `bun run db:generate` → writes a numbered SQL file under `drizzle/`
   (e.g. `0000_init.sql`, `0001_add_foo.sql`) plus `drizzle/meta/` snapshots.
3. Inspect the generated SQL. **Review the diff before committing** — this is
   the whole point.
4. Commit the `.sql` and the updated `drizzle/meta/` with the code change.

### Apply

- `bun run db:migrate` → `drizzle-kit migrate`. Applies only the pending
  migrations recorded in `__drizzle_migrations`. Safe to run repeatedly.

### Verify (CI)

- `bun run db:check` → `drizzle-kit check`. Fails if `src/db/schema.ts` is out
  of sync with the committed migrations (catches "I edited the schema but
  forgot to generate").

## 5. Config changes

`drizzle.config.ts`:

```ts
import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './src/db/schema.ts',
  out: './drizzle',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URL!,
  },
  // New — explicit, deterministic migrations table
  migrations: {
    table: '__drizzle_migrations',
  },
})
```

`package.json` scripts:

```jsonc
{
  "db:generate": "drizzle-kit generate",
  "db:migrate": "drizzle-kit migrate",
  "db:check": "drizzle-kit check"
  // "db:drop": "drizzle-kit drop"  // optional, dev-only
}
```

> `db:migrate` is now `drizzle-kit migrate` (non-interactive by design — no
> `--force` needed). The old `drizzle-kit push` is removed from the workflow.

## 6. Baselining the existing database (one-time)

The production DB was created via `push`, so it has tables but **no migrations
journal**. The first `drizzle-kit generate` will emit a full `CREATE TABLE` for
every table, which must **not** be re-run against a DB that already has them.

Procedure:

1. Locally, on a **fresh** scratch DB, run `db:generate` then `db:migrate` so
   the baseline migration (`0000_*.sql`) and the `__drizzle_migrations` table
   are produced correctly.
2. On the **existing** production DB, create the migrations table and mark the
   baseline migration as already applied, **without executing its SQL**:

   ```sql
   CREATE TABLE IF NOT EXISTS __drizzle_migrations (
     id SERIAL PRIMARY KEY,
     hash text NOT NULL,
     created_at bigint
   );

   INSERT INTO __drizzle_migrations (hash, created_at)
   VALUES ('<sha256 of the 0000_*.sql file>', extract(epoch from now()));
   ```

3. From then on, `db:migrate` will see the baseline as applied and only run
   subsequent migrations.

> **Verify during implementation:** confirm the exact `__drizzle_migrations`
> schema and the hash algorithm (sha256 of the migration SQL file content)
> against the installed `drizzle-kit` version before writing the baseline row.
> The safest approach is to let `db:migrate` create the table on the scratch DB
> and mirror its shape into production.

## 7. Deploy integration

`Dockerfile` currently runs `CMD ["bun", "run", "start"]` where `start` is:

```
varlock run -- bun run db:migrate && varlock run -- bun .output/server/index.mjs
```

With `db:migrate` now being `drizzle-kit migrate`, this boot flow becomes
idempotent and prompt-free. No Dockerfile change required beyond confirming the
release image still copies `drizzle.config.ts` and the `drizzle/` output folder:

```dockerfile
COPY --from=build /app/drizzle ./drizzle
```

## 8. Rollback & safety policy

- **Forward-only by default.** Drizzle does not generate down migrations. For
  routine additive changes this is fine.
- **Destructive changes** (drop table/column, rename, type change) must:
  1. be called out explicitly in the PR, and
  2. include a hand-written `-- down` SQL block in a comment (or a paired
     `*_down.sql` file) when a revert path is realistically needed.
- **Never hand-edit an already-applied migration.** Write a new migration
  instead.
- **Data-loss changes** (drop column/table) require a data migration step
  (backfill/copy) in the same or a preceding migration before the destructive
  statement.

## 9. Risks & mitigations

| Risk | Mitigation |
| --- | --- |
| Concurrent boot on multiple replicas racing to migrate | Run migrations as a separate one-shot step before the app (single migrator), or guard with a Postgres advisory lock. Out of scope for single-instance deploy, but note it. |
| Migration applied against a stale backup | Migrations are source-of-truth in git; restore = replay journal from a known good point. |
| `db:generate` drift between local and CI | `db:check` in CI as a required gate on every PR that touches `src/db/`. |
| Forgetting to commit `drizzle/meta/` | Commit it; add `drizzle/meta/` to `.gitignore` exceptions (do not ignore it). |

## 10. Acceptance criteria

- [ ] `bun run db:generate` produces a reviewed, committed SQL migration.
- [ ] `bun run db:migrate` applies pending migrations non-interactively and
      idempotently (no prompts, no `--force`).
- [ ] Production DB baselined once (step 6) so no `CREATE TABLE` re-runs.
- [ ] `bun run db:check` is wired into CI and passes.
- [ ] Boot no longer depends on an interactive schema push (502 class fixed
      structurally, not by `--force`).
- [ ] `README.md` (or `SPEC.md`) documents the new `db:*` commands and the
      "edit schema → generate → review → migrate" flow.
