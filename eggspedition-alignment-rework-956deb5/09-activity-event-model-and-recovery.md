# RW-009 — Activity Event Model, Ordering and Safe Recovery

**Priority:** P1  
**Maps to:** UX-009, UX-004, UX-005, UX-012  
**Primary outcome:** Activity is an accurate newest-first audit feed whose recovery actions restore exact domain state only when safe.

## Verified implementation

The current feed includes:

- natural-language activity copy;
- Today/Yesterday/date grouping;
- relative timestamps;
- loading skeletons;
- empty state;
- retry error state;
- a new-activity indicator mechanism;
- a Restore action for removed items.

## Discrepancies

### Activity feed remains stale after mutations

Changes made elsewhere in the application are not reliably reflected in Activity. Adding, incrementing, editing, completing, restoring or deleting an item can leave the Activity query showing its previous cached result until a manual page reload or an unrelated refetch occurs.

The mutation flows do not consistently update or invalidate the canonical Activity query key. The existence of a new-activity indicator does not solve this: the feed first needs to receive the newly created event.

This breaks Activity's core promise as an audit trail because a user can perform an action, open Activity immediately and not see it. It also makes the feed appear unreliable across tabs and household members.

### Ordering is reversed inside date groups

The service/query treats the first entry as newest, but `groupByDate` reverses each group. This presents oldest-first entries under Today/Yesterday despite the specification requiring newest-first.

### Email local-part is used as public identity

When no display name exists, the feed extracts text before `@`. That can reveal personal identity unexpectedly and can produce misleading names.

### Restore is lossy

Removed activity stores only `itemName`. Restore calls Add with quantity `1`, dropping the original quantity, category, store, checked state and item identity. It may merge into another item.

### Event schema is insufficient

The client event contains action, item name, timestamp and user identity. It lacks:

- entity/item ID;
- operation ID;
- before snapshot;
- after snapshot;
- quantity delta;
- event version;
- reversibility/expiry;
- server conflict status.

### “New activity” control dismisses rather than navigates

When new entries are eventually detected, the pill only clears the flag. It does not move the user to the new entries or preserve scroll context. More importantly, the indicator cannot compensate for the missing Activity-query synchronization described above.

### Cached-feed failure

The component replaces content with an error whenever query `error` is present. Background refresh errors should retain successfully cached feed data.

## Product decision

Activity events are immutable server records generated by domain mutations. They are not reconstructed from UI copy.

## Event schema

```ts
interface HouseholdActivityEvent {
  id: string
  householdId: string
  actor: {
    userId: string
    displayName: string | null
  }
  type:
    | 'item.created'
    | 'item.incremented'
    | 'item.updated'
    | 'item.completed'
    | 'item.restored'
    | 'item.deleted'
    | 'template.created'
    | 'template.updated'
    | 'template.deleted'
  entityType: 'groceryItem' | 'quickAddTemplate'
  entityId: string
  operationId: string
  occurredAt: string
  before: GroceryItemSnapshot | TemplateSnapshot | null
  after: GroceryItemSnapshot | TemplateSnapshot | null
  reversibleUntil: string | null
  reversedByEventId: string | null
}
```

The API may omit sensitive/internal fields from client responses but must preserve enough data server-side for exact recovery.

## Copy generation

Generate user-facing copy from typed events in one formatter.

Actor fallback order:

1. display name;
2. `You` for current user;
3. `A household member`.

Do not derive a display name from email.

Examples:

- `You added 2× Milk.`
- `A household member moved Apples to Produce.`
- `Anna completed Bread.`
- `You restored 3× Eggs.`

Metadata changes may show concise detail where useful.

## Ordering and pagination

Server returns:

```ts
ORDER BY occurred_at DESC, id DESC
```

Client:

- preserves response order;
- groups without reversing entries;
- orders groups newest date first;
- uses cursor pagination based on `(occurredAt, id)`;
- deduplicates by event ID;
- reconciles optimistic events by operation ID.

Never use localized labels as sort keys.

## Activity freshness and cache synchronization

Use one exported Activity query-key factory everywhere:

```ts
const activityKeys = {
  all: ['household-activity'] as const,
  feed: (householdId: string) =>
    [...activityKeys.all, householdId, 'feed'] as const,
}
```

Every successful domain mutation must make the corresponding Activity event observable without requiring a manual reload. Cover at least:

- item creation through the Add composer;
- Quick Add creation and quantity increments;
- item edits, including quantity/category/store changes;
- complete and restore;
- delete and recovery;
- Quick Add template create/update/delete when these are included in Activity.

Preferred flow:

1. The domain mutation and its Activity event are committed atomically on the server. A successful item mutation must never exist without its audit event.
2. The client mutation carries an `operationId`.
3. For same-client actions, insert a provisional Activity event into the Activity cache immediately or invalidate/refetch the feed as soon as the mutation succeeds.
4. Reconcile the provisional event with the server event by `operationId`; do not create duplicates.
5. For changes from another tab/device/member, a realtime signal invalidates the same canonical query key.
6. Opening the Activity route refetches stale data, including when the query was populated earlier in the session.
7. Window focus and network reconnection refetch when the Activity cache may be stale.

Do not scatter literal query-key arrays across components. Mutation hooks, realtime listeners and the Activity route must all target the same key factory.

A realtime notification is only a refresh trigger. The server remains the source of truth, and the client must refetch/reconcile rather than manufacturing permanent audit records from UI state.

## Restore eligibility

Server decides reversibility:

```ts
getActivityRecovery(eventId)
```

Eligible only when:

- event belongs to current household;
- event type supports inverse;
- entity has not changed incompatibly;
- event was not already reversed;
- retention window permits recovery.

For delete:

- restore exact snapshot;
- preferably undelete original item ID;
- otherwise return a conflict if active identity now exists;
- never silently merge through generic Add.

For update/complete:

- use before snapshot and expected version;
- show conflict if newer changes exist.

The client renders Restore/Undo only from `reversibleUntil`/capability returned by server.

## New-activity behavior

When events arrive while user is scrolled away from top:

- keep current scroll position;
- show `3 new activities`;
- activation scrolls/focuses the newest event and clears the count.

When already near top:

- insert without a pill;
- optionally announce one concise update.

Do not show a “new activity” indicator that only dismisses itself.

## Error/loading behavior

- Initial load: skeleton.
- Empty: product empty state.
- Background error with cached events: keep feed, show compact stale/retry notice.
- Initial error without data: full inline error.
- Restore failure: keep event visible and show action-level Retry/conflict.

## Localization

Use:

- `Intl.RelativeTimeFormat`;
- `Intl.DateTimeFormat`;
- locale-aware date boundaries;
- server ISO timestamps.

Avoid manually formatted `2m ago` strings as the only implementation if localization is a product requirement.

## Accessibility

- feed is a list of events;
- date headings create navigable sections;
- new-event button includes count;
- scrolling also moves programmatic focus to the target event;
- relative `<time>` includes full accessible datetime/title or nearby full date;
- Restore pending state is event-specific;
- live announcements are throttled.

## Acceptance criteria

- Entries are newest-first within every group.
- Group ordering is based on date values, not labels.
- Email local-parts never appear as display names.
- Deleted items restore exact quantity/category/store/identity.
- Restore is hidden/disabled when server says it is unsafe.
- Each mutation creates one event with operation ID.
- Add, Quick Add, edit, complete, restore and delete appear in Activity without a manual reload.
- Opening Activity immediately after a successful mutation shows the new event.
- Activity updates while already open when the current client performs a mutation.
- Changes from another tab/device/member invalidate and refresh the feed.
- Focus and reconnect recover a stale Activity cache.
- Optimistic activity does not duplicate after server event arrival.
- New-activity CTA moves to the new entries.
- Cached feed remains visible during background failure.
- Pagination does not duplicate or reorder events.
